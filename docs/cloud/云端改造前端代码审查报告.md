3. cloud-storage.ts:15 — Mock 模式硬编码，无法切换到真实 API

所有导出函数（testWebdavConnection、downloadWebdavFile、uploadWebdavFile 等）必经此开关，但硬编码为 true 且没有任何环境变量或配置驱动的方式将其切换为 false。上线前必须改为从 config 或环境变量读取。

4. cloud-app-sync.ts:137-149 + 337-357 — 媒体上传实际发送空 Blob
collectChangedMedia（第 337-357 行）创建的任务项中，blob 被设置为 new Blob()（空 Blob）。第 346-348 行的 blobPromise 变量计算后从未被 await 或使用。第 137 行 runWithConcurrency 直接使用 blob 字段调用 uploadWebdavFile(config, path, blob, blob.type)，导致上传到云端的媒体文件全部为 0 字节。核心同步功能完全失效。

5. cloud-app-sync.ts:404-420 — syncNonCanvasDomains 忽略了 domains 参数
函数签名接受 domains?: AppSyncDomainKey[]，但第 412 行始终调用不带域过滤的 syncAppDataToWebdav(config, onProgress)，参数形同虚设。调用方 cloud-sync.ts:133 期望只同步非 canvas 域，但实际同步了所有域（包含 canvas），导致重复同步。

6. app-config-modal.tsx:333 — Token 输入框通过不存在的 window 全局访问 store
const { setToken } = (window as any).useAuthStore?.getState() || {};
useAuthStore 是模块级 zustand store 导出，并未挂载到 window 上。这段代码始终走到 || {} 分支，setToken 为 undefined，用户输入 token 后永远不会被保存。Token 配置功能完全不可用。

Major（严重影响功能或数据正确性）
7. cloud-storage.ts — WebDAV URL 与云端 API URL 概念混淆
buildUrl（第 19-24 行）和 healthUrl（第 26-29 行）使用 WebdavSyncConfig.url 作为云端 API 基础 URL（构造 /api/storage/file?path=... 等路径）。但 WebdavSyncConfig 原本是用于 WebDAV 同步的配置，其 url 字段指向的是 WebDAV 端点。如果用户同时配置了 WebDAV 和云端，这两个使用同一字段会导致冲突。云端底座 URL 应有独立的配置字段。

8. image.ts:349-369 / video.ts:39-59 / audio.ts:16-36 — aiHeaders 三个副本完全重复
三份 aiHeaders 实现逻辑完全相同（仅 audio.ts 固定设置 Content-Type 略有差异）。如果网关鉴权逻辑需要变更，必须同步修改三个文件，极易遗漏。应提取到共享模块（如 model-gateway.ts 或独立 header 工具）。

9. image.ts:353 / video.ts:43 / audio.ts:20 — 使用 window.__AUTH_TOKEN__ 与 use-auth-store.ts 的 window.__APP_CONFIG__.authToken 不一致
三份 aiHeaders 读取 window.__AUTH_TOKEN__（第 353/43/20 行），而 use-auth-store.ts 的 readInitialToken 从 window.__APP_CONFIG__.authToken 读取（第 10 行）。两处使用不同 window 属性名，设置了 __APP_CONFIG__ 但未设置 __AUTH_TOKEN__ 时，aiHeaders 降级到 localStorage 读取，但如果是运行期注入则无法生效。

10. model-gateway.ts:109-113 — 网关底座 URL 从 env/window 读取，但 Cloud Tab 存储到 webdav.url
gatewayBaseUrl() 读取 window.__APP_CONFIG__.gatewayUrl 或 VITE_GATEWAY_URL 环境变量，而 Cloud Tab（app-config-modal.tsx:323-326）将用户输入的网关 URL 存入 webdav.url（通过 updateWebdavConfig("url", ...)）。两套来源不互通：用户在 UI 配置的网关 URL 对 fetchGatewayModels 和 ensureGatewayChannel 无效。

11. model-gateway.ts:64-84 — ensureGatewayChannel 在启动路径中从未被调用
网关虚拟渠道的创建函数 ensureGatewayChannel 只会在 UI 中手动调用的地方触发（model-select-modal.tsx、app-config-modal.tsx）。如果用户从未打开配置弹窗，网关渠道不存在，此时 resolveModelChannel 对 gateway::xxx 格式的 model value 会 fallback 到 config.channels[0]，导致 isAiConfigReady 的网关分支（第 210 行 channel.id === "gateway"）永远走不到，这又要求检查该 fallback 渠道的 apiKey，从而导致网关模型被判断为 "未配置"。

12. cloud-sync.ts:42-54 — store 订阅条件过于宽泛，每次 hydration 后的任何变更都触发同步
Canvas 订阅回调（第 43-46 行）的条件 state.hydrated && state.projects.length >= 0 中，>= 0 恒为 true，等价于仅检查 hydrated。Asset 订阅同理（第 50-53 行）。这意味着 hydration 完成后，store 的任何 setState 都会调用 markDirty() 并触发同步调度，包括 paint/selection 等无关变更。应添加更精确的脏检查（如比较 projects/assets 的引用或 updatedAt）。

13. cloud-sync.ts:81 — sendBeacon 使用硬编码路径
beforeunload 处理器中 navigator.sendBeacon("/api/storage/flush", ...) 发送到固定绝对路径 "/api/storage/flush"，未考虑云端底座的实际 URL。如果前端部署在与云端 API 不同的源，此请求永远失败。应使用 getSyncConfig() 中的 URL 拼装完整地址。

14. main.tsx:15 — initCloudSync() 在 React 渲染前调用
第 15 行的 initCloudSync() 执行在 createRoot(...).render() 之前（第 19 行）。虽然 zustand 支持此用法，但其中 100ms 间隔的 trySubscribe 轮询（cloud-sync.ts:29）会在 UI 渲染前持续运行，增加不必要的启动延迟和可能的同步尝试。

15. model-select-modal.tsx:68,71 — 不应使用动态 import
const { refreshGatewayModels } = await import("@/services/api/model-gateway");
const { useConfigStore } = await import("@/stores/use-config-store");
这两个模块很可能在应用启动时已加载完毕。使用 await import() 引入额外的 async 开销，且可能导致模块加载时序问题（虽然概率低）。应改为首部静态 import。

16. cloud-sync.ts:63-88 — lifecycle hooks 未提供清理机制
registerLifecycleHooks 添加了 visibilitychange 和 beforeunload 监听器，但没有相应的 removeEventListener。虽然当前只调用一次不会泄漏，但如果后续需要初始化/销毁周期（如在测试中或 HMR 场景），会导致监听器重复累积。

21. cloud-app-sync.ts:195-199 — 墓碑排序比较器不规范

22. cloud-sync.ts:120-145 — doSync 在 isSyncing=true 时静默返回但不标记脏
