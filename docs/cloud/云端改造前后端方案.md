# Infinite-Canvas 云端改造方案(前端改动 + 后端接口契约)

> 基于 infinite-canvas 开源项目(纯浏览器端 Web 应用,Vite + React 19 + Zustand,无后端)的云端化改造。
> 目标:
> 1. 画布数据(含图片/视频/音频 Blob)从"仅浏览器 IndexedDB"升级为"云端副本 + 本地缓存"
> 2. AI 模型调用从"用户自配 baseUrl/apiKey"升级为"后端模型网关,用户只选模型"
>
> 原则:**改动收敛在前端少数文件,与上游代码库保持最小冲突面,便于跟进上游更新。**

---

## 0. 架构总览

```
                        浏览器前端
┌─────────────────────────────────────────────────────┐
│ IndexedDB(本地缓存层,保留不动)                          │
│   ├─ app_state      画布/资产 JSON                     │
│   ├─ image_files    图片 Blob                          │
│   └─ media_files    视频/音频 Blob                     │
│                                                      │
│ 自动同步层(新增) ──订阅 store 变化──→ 云端存储副本       │
│ AI 调用层(虚拟 gateway 渠道) ──────→ 模型网关            │
└───────────────┬──────────────────────┬───────────────┘
                │ 同一 token             │ 同一 token
                ▼                       ▼
      ┌───────────────────┐   ┌────────────────────┐
      │ /api/storage/*   │   │ /api/models        │
      │ 哑文件存储(4 接口) │   │ /v1/* OpenAI 代理   │
      └───────────────────┘   └─────────┬──────────┘
                                 上游: OpenAI/Gemini/可灵/…
```

两条链路完全解耦:
- **AI 生成流**(模型处理):浏览器 → 网关 → 上游服务商,与存储无关
- **持久化流**(保存):IndexedDB → 云端存储副本,与模型无关

> 存储定位决策:**云存储为唯一事实源,浏览器(IndexedDB + HTTP 缓存)仅为缓存层**,不做离线保障。

# 第一部分:后端接口契约(交后端同事)

## 1. 通用约定

- 鉴权:所有接口 `Authorization: Bearer <token>`;token 由账号体系签发(内网部署可固定 token)
- 数据格式:除文件传输外均为 JSON(`Content-Type: application/json`)
- 错误响应统一格式:

```json
{ "error": { "code": "NOT_FOUND", "message": "文件不存在" } }
```

- CORS:前端为浏览器直连。推荐前后端同域反代(如 `/api`、`/v1` 直接同域),否则需配置:
  - `Access-Control-Allow-Origin: <前端域名>`
  - `Access-Control-Allow-Methods: GET, PUT, POST, DELETE, OPTIONS`
  - `Access-Control-Allow-Headers: Authorization, Content-Type`
  - 正确响应 OPTIONS 预检请求

## 2. 云端存储接口(替代 WebDAV,4 个必需 + 2 个可选)

设计为**基于路径的哑文件存储**:后端不理解文件内容,只按路径存取二进制。路径根目录按 token 对应的用户隔离(多用户天然隔离)。

> ⚠️ **已决策:三个风险点的最终决策见附录 F1/F2/F3。**

### 2.1 连接测试(必需)

```
GET /api/storage/health
Authorization: Bearer <token>
```

响应:

| 状态 | Body |
|---|---|
| 200 | `{"ok": true, "user": "xxx", "usage": {"used": 123456, "quota": 1073741824}}` |
| 401 | token 无效 |

### 2.2 下载文件(必需)

```
GET /api/storage/file?path={relativePath}
Authorization: Bearer <token>
```

参数:

| 参数 | 类型 | 说明 |
|---|---|---|
| path | string(query) | 相对用户存储根的路径,`/` 分隔,如 `canvas/files/image:V1StGXR8.png` |

响应:

| 状态 | 说明 |
|---|---|
| 200 | 二进制 body,`Content-Type` 为上传时保存的 MIME |
| 404 | **不存在(前端约定 404 = null,不算错误)** |
| 401 | 未授权 |

安全要求:校验 path,拒绝 `..` 越界。

**必须支持 `Range` 请求头**(返回 `206 Partial Content` + `Content-Range`):直存模式下 `<video>` 直接播放云端 URL,不支持 Range 则视频拖进度条失效、seek 触发整段重下。建议同时支持 `HEAD` 与缓存相关头(`ETag`/`Last-Modified`),配合浏览器 HTTP 缓存。

### 2.3 上传文件(必需)

```
PUT /api/storage/file?path={relativePath}
Authorization: Bearer <token>
Content-Type: <实际 MIME 或 application/octet-stream>
Body: 原始二进制
```
语义要求(**与 WebDAV PUT 一致,同步引擎依赖此语义**):
- 同路径重复上传 = **幂等覆盖**
- **父目录隐式创建**(前端不再发任何建目录请求)
- 大文件流式落盘,勿全量缓冲
- **乐观锁**:请求须支持 `If-Match: <etag>` 请求头。服务端收到 `If-Match` 头时校验 etag,不匹配返回 412 `PRECONDITION_FAILED`;未传 `If-Match` 头时视为首次写入(不存在则创建、存在则覆盖)。
  - 前端在 A3 实现收到 412 后重读→重新合并→重试(循环上限 3 次)
  - **首次写入**(无 etag)√;**覆盖写入**(读到的 etag)必须带 `If-Match`

响应:

| 状态 | Body |
|---|---|
| 200 | `{"path": "...", "bytes": 12345, "etag": "abc"}` |
| 401 / 413 | 未授权 / 超配额 |

### 2.4 删除文件(必需)

```
DELETE /api/storage/file?path={relativePath}
Authorization: Bearer <token>
```

响应:200(已删除或本就不存在,**建议 404 也返回 200**,简化前端)。

### 2.5 批量上传(可选,强烈建议)

单个画布可能几十张图,逐个 PUT 慢。multipart 批量:

```
POST /api/storage/batch
Content-Type: multipart/form-data
  part "meta" (JSON): [{"path": "canvas/files/a.png", "part": "f1"}, ...]
  part "f1": 二进制
  part "f2": 二进制
→ 200 {"results": [{"path": "...", "bytes": 123, "status": "ok"}]}
```

### 2.6 列表/统计(可选,调试与对账)

```
GET /api/storage/list?prefix=canvas/files/
→ {"files": [{"path": "...", "bytes": 123, "etag": "..."}]}
```

### 2.7 远端目录结构(前端约定,后端无需理解内容)

```
{namespace}/canvas/index.json           # 画布索引(极小):{app, domain, projects:[{id,title,updatedAt}], deleted:[{id,deletedAt}]}
{namespace}/canvas/projects/{id}.json  # 每画布一个完整 JSON(nodes/connections/chatSessions/...)
{namespace}/canvas/files/{safeFileName(storageKey)}.{ext} # 画布域媒体文件(扁平,按 storageKey 全局去重;冒号等非法字符替换为下划线)
{namespace}/canvas/files.json           # 画布域媒体清单:{files:[{storageKey,path,mimeType,bytes}]}
{namespace}/assets/manifest.json        # 资产域清单(单文件,通常较小)
{namespace}/image-workbench/manifest.json
{namespace}/video-workbench/manifest.json
```

要点:
- **画布按项目拆分文件**:自动同步只上传被编辑的那一个 `projects/{id}.json`,而非全量;两台设备编辑不同画布互不冲突
- **画布发现走 index.json**(普通文件存取),不需要画布专用列表接口;同步时"读远端索引→按 id/updatedAt 合并→写回",墓碑防复活
- **画布媒体走 `canvas/files.json` 清单**:清单记录每个媒体的 storageKey/路径/大小;同步时"本地缺 Blob 就按清单补下载、远端大小一致就不重传";前端**不发起远端删除**(见 F3 软删除决策)
- 后端始终只做按路径的存取,不理解以上任何结构

### 2.8 非功能性要求
- 单文件上限 ≥ 1GB(视频 Blob 可能很大)
- **乐观锁**:PUT 必须支持 `If-Match: <etag>` 请求头,冲突返回 412(详见 2.3)

### 2.9 同步信号(可选)

前端在 `beforeunload` 时用 `navigator.sendBeacon` 发一个"有未同步改动"的信号,便于后端即时落盘:

```
POST /api/storage/flush
Body: {"dirty": true}      # 仅信号,不携带数据
→ 200/204 均可
```

后端可以忽略该端点(返回 404 不影响前端,前端不读响应体)。

> - 前端用 `sendBeacon(url, JSON.stringify(...))` 发送的是**字符串**,浏览器带的是 `Content-Type: text/plain;charset=UTF-8`,后端不要按 `application/json` 严格校验
> - **该请求不带 `Authorization`**(`sendBeacon` 无法设置请求头),所以后端要么把它当未鉴权信号处理,要么直接返回 401/404 忽略——两者对前端都没差别;也不要用它承载任何需要可信身份的逻辑
> - **不做该端点也没有功能影响**:前端不读响应、不重试、不等结果;数据本身已落在 IndexedDB,"下一次启动无条件同步"与编辑停止防抖(30s)都会把它上传

## 3. 模型网关接口

### 3.1 模型列表(必需)

```
GET /api/models
Authorization: Bearer <token>
→ 200 {
  "models": [
    { "id": "gemini-3-pro-image", "name": "Gemini 3 Pro 图片", "capability": "image" },
    { "id": "kling-3.0",          "name": "可灵 3.0",          "capability": "video" },
    { "id": "gpt-5.5",            "name": "GPT-5.5",           "capability": "text" },
    { "id": "gpt-4o-mini-tts",    "name": "TTS 语音",          "capability": "audio" }
  ]
}
```

**`capability` 取值必须对齐前端四值枚举:`"image" | "video" | "text" | "audio"`**,前端按此过滤下拉列表。

### 3.2 OpenAI 兼容代理端点(必需)

网关对外**只暴露 OpenAI 格式**,后端负责把 Gemini/可灵等各家协议翻译掉(含持有各上游真实 Key、模型名路由、计费/限流)。前端调用端点全集:

| 端点 | 方法 | 用途 | 特殊要求 |
|---|---|---|---|
| `/v1/images/generations` | POST | 文生图(JSON) | — |
| `/v1/images/edits` | POST | 图生图(**multipart FormData**,含 `image[]`) | 流式读取 body |
| `/v1/responses` | POST | 文本对话(`stream: true`) | **SSE 流式必须透传,不能缓冲完再回** |
| `/v1/videos` | POST | 视频任务创建(**FormData**:`model/prompt/seconds/size/generate_audio/watermark/mode/first_frame/last_frame/image[]` 等) | — |
| `/v1/videos/{id}` | GET | 视频任务轮询 | 长任务,后端保持任务状态直至完成/失败 |
| `/v1/videos/{id}/content` | GET | 视频结果下载(blob,可能几百 MB) | 流式响应,勿全量缓冲 |
| `/v1/audio/speech` | POST | TTS(JSON:`model/input/voice/response_format/speed/instructions`,响应为 blob) | — |
| `/v1/models` | GET | (可选)可复用 `/api/models` 的数据 | — |

请求中的 `model` 字段值即 `/api/models` 返回的 `id`,由后端路由到对应上游。

**鉴权**:所有 `/v1/*` 同样带 `Authorization: Bearer <token>`;上游服务商的 Key 永不出后端。

### 3.3 服务端直存(可选增强,视频场景强烈建议)

**问题**:基线方案中,上游生成的 100MB 视频 = 浏览器先下载 100MB(GET content)→ 存 IndexedDB → 自动同步再上传 100MB(PUT 云存储),用户下行 + 上行带宽各走一遍。

**方案**:结果文件由**后端直接写入用户云存储**(内网/同机房直传,零用户带宽),任务响应携带直存信息,前端节点立即用云端 URL 播放,不再往浏览器落一份副本(IndexedDB 仅作缓存):

```
流程:
① 前端 POST /v1/videos(参考图经网关送上,与直存无关)
② 后端:调上游生成 → 拿到结果 → 服务端直存为 canvas/files/video:V1St....mp4
③ 轮询响应新增字段:
GET /v1/videos/{id}
→ { "status": "completed",
    "storageKey": "video:V1St...",     # 后端已直存的 storageKey(沿用 image:/video: 前缀约定)
    "path": "canvas/files/video:V1St....mp4",
    "bytes": 104857600 }
④ 前端:节点 metadata.storageKey = "video:V1St..."
        content = 云端 URL(/api/storage/file?path=...),画布立刻可播放
        (IndexedDB 仅作缓存:曾打开过的画布再次渲染更快;不做离线承诺,也不做懒缓存)
```

**要点**:
- **定位决策**:IndexedDB/浏览器缓存仅为**缓存层**,不做离线保障——云存储是唯一事实源
- `storageKey` 指针体系不变,变的只是 Blob 来源(浏览器上传 → 后端直存 + 前端按需拉取);GC、导出不受影响
- 前端同步时对服务端直存的文件只写入 `canvas/files.json` 清单条目、不上传(清单里的 bytes 与本地一致即跳过上传)
- 若实现此增强,`GET /v1/videos/{id}/content` 仍保留(导出/降级下载用)

### 3.4 服务端引用(与 3.3 配套,推荐一并实现)

生成请求的参考图/参考视频**不必经过浏览器上传**,直接引用用户云存储中的文件:

```
POST /v1/videos (FormData),二选一或混用:
  方式 A(现有): image[]  = 二进制文件          ← 本地新图/尚未同步的图
  方式 B(新增): image_ref[] = "image:V1St..."  ← 引用云存储中的 storageKey(或完整 path)

POST /v1/images/edits 同理: image_ref[] / image[]
POST /v1/responses(文本对话)同理:引用型 image part
```

后端职责:收到 `*_ref` 后从该用户云存储服务端读取文件,转发上游。**文件零浏览器带宽。**

前端判断逻辑:参考图的 storageKey 已在远端 manifest → 传 ref;否则(新图未同步)走方式 A 上传。两条路并存,兼容自动同步的 30s 防抖窗口。

## A. 云端存储改造

### A0. 设计原则

- **IndexedDB 保留**(它是性能必需的本地缓存层,不做离线保障,不是被替换的旧存储)
- 云端是"自动维护的副本":同步模块订阅 zustand store 变化,自动触发
- 数据模型(`storageKey` 指针体系)**零改动**
### A1. 新建 `web/src/services/cloud-storage.ts` — HTTP 传输层(核心改动)

**自包含新文件,不碰上游 `webdav-sync.ts`。** 核心导出与 `webdav-sync.ts` 同名同签名,`app-sync.ts` 的传输层 import 已切到本文件,并新增 `skipCanvas` 选项(云端改造后 canvas 域由 `cloud-app-sync.ts` 独立同步,避免同一域两套布局重复同步):

| 函数 | WebDAV 实现 | HTTP 云存储实现 |
|---|---|---|
| `testWebdavConnection` | PROPFIND Depth:0 | `GET /api/storage/health` |
| `downloadWebdavFile` | WebDAV GET | `GET /api/storage/file?path=` |
| `uploadWebdavFile` | PUT + MKCOL 建目录 | `PUT /api/storage/file?path=` + `If-Match` 乐观锁 |
| `ensureWebdavDirectory` / `ensureWebdavDirectoryPath` / `webdavDirectoryExists` | MKCOL/PROPFIND | **新传输层不实现**(后端隐式建目录);`webdav-sync.ts` 侧保留,供 WebDAV 页签使用 |
| `deleteWebdavFile`(新增) | — | `DELETE /api/storage/file?path=` |
| 鉴权 | Basic Auth | `Bearer <token>` |

**迁移路径(现状)**:`app-sync.ts` 的 import 已由 `webdav-sync` 改为 `cloud-storage`;`app-config-modal.tsx` 同时引用两者——「云端存储」页签用 `cloud-storage`,「WebDAV」页签保留 `webdav-sync`(旧手动同步仍可用)。

### A2. 新建 `web/src/services/cloud-sync.ts`(~180 行,自动同步调度)

自包含新文件,便于上游合并。职责:
- 启动时调 `initCloudSync()`:等待 zustand persist hydration 完成后,通过 `useCanvasStore.subscribe` / `useAssetStore.subscribe`(或 `getState()` 轮询)检测变化
  - ⚠️ `useCanvasStore` 是 `persist` 包裹的 store,subscribe 需要等 `hydrated === true` 后再注册;或使用 `subscribeWithSelector` 中间件
- 防抖自动同步:编辑停止 30s(可配)后触发,复用 `cloud-app-sync.ts` 的逐画布同步 + `cloud-storage.ts` 传输层
- `visibilitychange` 时按 5s 防抖 flush;`beforeunload` 时用 **`navigator.sendBeacon`** 只发 `POST /api/storage/flush` 脏标记信号(信号型,不做数据同步,避免异步 fetch 在页面关闭时被丢弃)
- 同步互斥锁(防自动/手动并发重入)+ 脏标记
- 启动恢复:hydrated 后**无条件同步一次**——本地为空时全量拉取,本地非空时按 `updatedAt` 拉取远端较新画布并补齐缺失媒体(复用 `cloud-app-sync.ts` 的合并逻辑)
- 非 canvas 域(assets/image-workbench/video-workbench)同步仍复用 `app-sync.ts` 的 `syncDomain`;启动时另调 `ensureGatewayChannel()` 并在后台 `refreshGatewayModels()` 刷新网关模型列表
### A3. 新建 `web/src/services/cloud-app-sync.ts` — canvas 域逐画布同步(不与上游冲突)

**`app-sync.ts` 仅小改**(传输层 import 切到 `cloud-storage`、新增 `skipCanvas` 选项、key 收集改引共享实现),同步流程本身不动:per-canvas 同步实现在自包含新文件中:

- canvas 域从\"单 manifest 全量\"改为 per-canvas 布局(见后端契约 2.7):
  - 读 `index.json` 合并索引(按 id/updatedAt,墓碑防复活)
  - 远端新的:逐画布 `GET /api/storage/file?path=canvas/projects/{id}.json` 合并;本地脏的:只 `PUT projects/{id}.json`
  - 索引写回前必须重读远端 + If-Match 乐观锁重试(循环上限 3 次)
  - 媒体:维护 `canvas/files.json` 清单(记录 storageKey/路径/mimeType/bytes),"本地缺 Blob 就按清单补下载、远端 bytes 一致就不重传"

- 改动规模:约 480 行新文件,换来增量带宽 + 列表秒开 + 画布级冲突隔离

## F1. index.json 并发写竞争 — **已决策:乐观锁**

✅ **最终决策**:方案 **A(乐观锁)**。PUT 必须支持 `If-Match`(详见 2.3 接口契约),前端收到 412 后重读→重新合并→重试(循环上限 3 次)。

**问题**(供参考):A3 的"索引写回前重读远端合并"只能缩小竞争窗口,不能消除。两台设备同时完成"读旧索引 → 合并 → PUT"时,后写的覆盖先写的,**先者新建的画布条目直接丢失**(经典 TOCTOU 竞态):

```txt
设备A: GET index.json(v1) ──合并自己的新画布──→ PUT index.json
设备B:   GET index.json(v1) ──合并自己的新画布──→ PUT index.json   ← A 的条目被覆盖
```

**候选方案**(已最终决策,记录备查):
| 方案 | 做法 | 评价 |
|---|---|---|
| A. 乐观锁(**已选**) | PUT 支持 `If-Match: <etag>`,不匹配返回 412;前端收到 412 → 重读 → 重新合并 → 重试(循环上限 3 次) | 前端加重试循环(~20 行),后端仅比对 etag,哑存储边界不破坏 |
| B. 条目级合并 | 后端对 index.json 做按 id 的字段级合并 | 轻微破坏哑存储边界,后端需理解索引结构,不推荐 |
| C. 接受丢失 | 单用户低频场景,概率极低 | 不符合"云存储为唯一事实源"的定位 |

## F2. "删除 vs 编辑"竞态语义 — **已决策:墓碑无条件赢**

✅ **最终决策**:**墓碑无条件赢(删除优先)**。合并逻辑中:存在墓碑 → 直接判删,不再比较 `updatedAt`。

**问题**(供参考):设备 A 删除画布,设备 B 此刻正开着它编辑并推送——B 的 `updatedAt` 更新,按"新者胜"合并规则**画布复活**。上游墓碑机制只防"旧数据合回",没有定义删除与更新的优先级。

**候选语义**(已决策,记录备查):
| 语义 | 行为 | 适用 |
|---|---|---|
| **墓碑无条件赢(已选)** | 删除是不可逆操作,编辑丢失 | 简单可预期;用户删了就是删了,B 端下次同步看到墓碑直接本地清除 |
| 编辑赢 | updatedAt 新者胜,删除视为失败 | 尊重最新劳动,但"删不掉"体验更差 |
| 冲突提示 | 前端检测到墓碑 vs 更新冲突,弹窗让用户选 | 体验最好,但同步链路要加 UI 分支,复杂度高 |

## F3. 远端文件清理 — **已决策:后端软删除,前端不做远端 GC**

✅ **最终决策**:后端对文件不执行真正的删除,仅标记删除状态(软删除/逻辑删除)。前端不发起远端 DELETE 调用,不再做远端 GC。

**变更说明**:原本 F3 的风险源于"本地引用扫描决定远端删除,collectStorageKeys 不一致导致误删"。由于后端改为软删除:
- **误删风险消除**:文件不会被物理删除,"误删"最多是无引用文件残留
- 前端 A3 不再调用 `deleteWebdavFile`(或改为后端标记接口)
- 后端可定期清理标记删除超过 N 天的文件(运营策略,非接口必须)
- `collectStorageKeys` 多份实现的问题降级为工程整洁度问题,不再阻塞开发

**净效果**:实际与上游产生实质性冲突的文件 **3 个**(`use-config-store.ts`、`app-config-modal.tsx`、`app-sync.ts`),另有 4 行级差异(`canvas-generation-helpers.ts`)与两处 GC 收集函数收敛(`image-storage.ts` / `file-storage.ts`);其余均为新增文件或单行改动。相比原方案(改 `webdav-sync.ts` + 重构 `app-sync.ts`),冲突面仍大幅缩小。

## G3. 已知且接受的次级影响

- **缩略图**:上游 `image_previews` 为纯本地设计,新设备首次打开画布需重新生成全部缩略图(CPU + 首屏变慢),可接受
- **同步非实时**(启动拉取 + 30s 防抖):两设备交替使用没问题;**同时双开**则落入 D1 的粗粒度冲突场景,单用户定位下够用

**结论:目标 1/3/4(存储上云、HTTP 接口、模型网关)完全满足;目标 2 原则保持但边界有意扩张(见 G2);F1~F3 风险点闭环 + 认证形态拍板后即可开工。**

# 附录 H:canvas 域远端布局决策分析(per-canvas vs 单 manifest)

> 讨论记录:是否确定"一个画布一个 manifest"是最优?以下为方案比选。

## H1. 候选布局

| | 方案 A:单 manifest(canvas 域一个 JSON) | **方案 B:per-canvas(index.json + projects/{id}.json)** | 方案 C:超精细(节点级/操作日志) |
|---|---|---|---|
| 远端形态 | `canvas/manifest.json` 装全部项目 | 极小索引 + 每画布一个文件 | 每节点/每次操作一个文件 |
| 自动同步带宽 | **O(全量)**:改一个节点也重传所有画布 JSON | **O(改动)**:只传被编辑的画布 | O(操作),但需 CRDT/OT |
| 首次换设备 | 一次下载全量 | 先拉索引(列表秒出),再按需逐画布拉取 | 复杂 |
| 冲突面 | 所有设备竞争同一个文件 | 不同画布 = 不同文件,互不冲突 | 最小 |
| 后端复杂度 | 哑存储不变 | 哑存储不变(index.json 仍普通文件) | 需理解结构或引入同步引擎 |
| 前端改动 | 最小(沿用上游逻辑) | canvas 域重写 ~480 行 | 不可行(等于重写项目) |
| 项目规模上限 | ~50 个画布后明显变慢 | 数百~上千画布无压力 | — |

## H2. 为什么 B 是当前约束下的最优

1. **A 的死穴在自动同步**:手动快照时代 A 够用;接入 30s 防抖自动同步后,每次编辑停止都全量重传,50 画布 × 200KB = 每次 10MB——用户加一个节点也要 10MB 上行,不可接受
2. **C 超出必要复杂度**:节点级合并需要操作转换/CRDT,与"哑存储 + 单人单设备编辑"的定位不匹配,是重写级工作量
3. **B 的代价明确且一次性**:canvas 域重写 ~480 行(G2 已记录);换来增量带宽、列表秒开、画布级冲突隔离三个长期收益
4. **B 不破坏哑存储**:index.json 对后端仍是"按路径存取的普通文件",零业务理解,这是整个方案的根基

## H3. B 的已感知缺点(诚实记录)

- index.json 成为新的并发竞争点(单 manifest 也有同样问题,只是 B 让它更早暴露)→ 由 F1 乐观锁闭环
- 同一画布内仍是整文件覆盖,节点级冲突依然粗粒度 → 与单 manifest 相同,未恶化;真需要时是未来的 CRDT 演进方向
- 前端复杂度增加:需要维护"索引合并"与"画布合并"两级逻辑

**决策:采用方案 B(per-canvas)。若项目规模确定长期很小(<20 个画布)且不接受 app-sync 重写,方案 A 仍是可退守的简化选项——但自动同步体验会显著劣化,不推荐。**
